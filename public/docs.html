Overview

What ferrox is

ferrox serves static files, proxies /api to a configurable backend (including WebSocket upgrades), and does both with the safety checks a real server needs: path traversal protection, request size limits, method gating, and a Slowloris mitigation - all hand-built on top of tokio and hyper 1.x, with no web framework in between.

Routes

What's exposed

GET/Status page
GET, HEAD/healthReturns 200 if the server is up
GET, HEAD/helloPlain-text response, useful for smoke tests
any/api/*Reverse-proxied to the configured upstream, including WebSocket upgrades
GET, HEAD/*Static files served from ./public

TRACE is rejected everywhere with 405 - it has no legitimate use here and has a history of enabling cross-site tracing attacks in browsers. Every other method not listed above on a given route also returns 405, except /api/*, which stays permissive since it's a transparent proxy to a backend that may implement its own methods.

Security

What's actually enforced

Path traversal

Any request path containing a literal .. segment is rejected outright. As defense in depth, every resolved file path is canonicalized and checked against the canonicalized public root before being served - this also catches symlink-based escapes, not just literal ../ sequences.

Request body limits

Requests through /api are capped at 10 MB. A declared Content-Length over the limit is rejected immediately with 413, before any of the body is read. As defense in depth against chunked-encoding bodies with no declared length, the body is also streamed through a byte-counter that aborts if the real size exceeds the limit regardless of what was claimed.

Slowloris mitigation

Every connection is wrapped in a read-stall timeout: if no bytes arrive for 30 seconds, the connection is closed. The timer resets on any progress, so a genuinely slow-but-active client (a real upload on a bad connection, a WebSocket exchanging periodic frames) is unaffected - only a connection making no progress at all gets cut. This is a first-layer mitigation, not a complete one: it doesn't enforce a minimum throughput, only that something arrives periodically.

Startup checks

ferrox checks that its public directory actually exists before binding a socket or accepting any connections, failing fast with a clear error rather than panicking on the first request if the working directory is wrong.

Response headers

Every response - including error responses - carries X-Content-Type-Options: nosniff, X-Frame-Options: DENY, X-XSS-Protection, and Referrer-Policy: strict-origin-when-cross-origin.

Performance & reliability

How it stays fast

In-memory caching

Files under 5 MB are cached in memory after their first request, keyed by resolved path. Cache entries are invalidated by comparing the file's modification time on every request - editing a file on disk is picked up immediately, with no restart or manual invalidation needed.

Streaming for large files

Files over the cache threshold are streamed directly from disk in fixed-size chunks rather than buffered fully into memory first, and are never cached. Memory use per request stays constant regardless of file size.

HTTP Range requests

Single-range Range requests (bytes=0-99, bytes=500-, bytes=-100) are supported and return 206 Partial Content with a correct Content-Range header, for both cached and streamed files. Multi-range requests fall back to a full 200 response; an out-of-bounds range returns 416.

Connection pooling

/api requests reuse persistent keep-alive connections to the upstream via a pooled HTTP client, instead of opening a fresh TCP connection per request.

Graceful shutdown

On SIGINT or SIGTERM, ferrox stops accepting new connections immediately but waits (up to 10 seconds) for in-flight requests to finish before exiting.

WebSocket proxying

Transparent upgrade relay

A request to /api/* with Connection: Upgrade and Upgrade: websocket is relayed to the configured upstream: ferrox performs the upgrade handshake on both legs, then pipes bytes bidirectionally between the client and the backend for the life of the connection.

Configuration

ferrox.conf and overrides

Configuration is a small TOML file:

listen = "0.0.0.0:3000"
proxy_upstream = "127.0.0.1:8000"

If no config file exists at the resolved path, ferrox creates one with these defaults on first run.

Resolution order

  • --config <path> or --config=<path> command-line flag
  • FERROX_CONFIG environment variable
  • ./ferrox.conf (default)

An explicitly given path (flag or env var) that doesn't exist is treated as an error rather than silently auto-created - only the implicit default is auto-generated.

Static root

Set FERROX_PUBLIC_DIR to serve files from somewhere other than ./public.

Testing

cargo test

ferrox has both unit and integration test coverage:

  • Unit tests for pure logic with no I/O - Range header parsing, the path traversal guard - run in milliseconds.
  • Integration tests spin up a real ferrox instance on an OS-assigned free port and exercise it with raw HTTP requests over a socket: routing, method gating, traversal, Range requests, the WebSocket relay, and the read-stall timeout are all verified end to end against actual running code, not mocked.
cargo test

Deployment

Running it for real

As a plain binary

ferrox has no runtime dependency on Docker or anything else - a built binary, a public/ directory, and an optional config file are all it needs.

cargo build --release
./target/release/ferrox

As a systemd service

[Unit]
Description=ferrox web server
After=network.target

[Service]
Type=simple
User=ferrox
WorkingDirectory=/opt/ferrox
ExecStart=/opt/ferrox/ferrox
Restart=on-failure
RestartSec=2

[Install]
WantedBy=multi-user.target

Behind Caddy (TLS + rate limiting)

A Caddy reverse proxy in front of ferrox handles automatic TLS via Let's Encrypt and, with the mholt/caddy-ratelimit plugin, per-IP rate limiting - both configured outside of ferrox itself, at the edge.

A Docker Compose stack (ferrox + a custom Caddy build with the rate-limit plugin) is included in the repository for this, but Docker is optional - Caddy and its plugins install and run natively just as well.

Maintenance

Keeping dependencies honest

Dependency vulnerabilities are checked with cargo audit against the RustSec advisory database - worth running after any dependency bump, not just occasionally.

cargo audit
